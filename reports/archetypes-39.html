A hypervisor now re-evaluates each microVM guest it starts, filling in the credential file paths the guest declared but never supplied

Two halves of a credential-delivery design lived in separate repositories with nothing between them: a guest listed the credentials it expects and left the values empty, while the host code asserted that both lists agree without ever being handed a guest. This change adds the connecting module, two evaluation-time checks, and one dependency-pinning line. It accepts host wiring and generated systemd and QEMU text that no machine has executed, because nothing in this fleet selects the microVM runtime yet.

How microvm.nix starts a guest, and where this framework's two halves live

A microVM guest is a complete machine description computed on the host before anything runs, which lets the host fill in facts only the host knows.

This change is written in Nix, whose programs compute build recipes rather than run anything. Evaluating an expression produces a derivation: a description of how to build one result, named by a content-addressed path such as /nix/store/66i3c5xm…-nixos-system-allod-dev. Identical output means an identical path, so comparing paths answers whether anything changed. NixOS builds a whole Linux machine this way: fragments called modules merge into one settings tree whose top is a derivation named system.build.toplevel.

microvm.nix, the outside project, ships two independent halves: a guest half that makes an ordinary NixOS machine bootable as a lightweight virtual machine, and a host half that generates the systemd services starting and stopping each guest. This repository, allod/archetypes, used the guest half and never the host half.

Definition

A hypervisor is the physical machine that runs virtual machines; a guest is one of the machines it runs. Here the example hypervisor is nexus and the example guest is allod-dev.

The three ways a host can name a guest

microvm.nix lets a hypervisor describe each guest under microvm.vms.<name> and accepts three answers for what that guest is. Upstream computes some of its own defaults from which one you used.

This repository already exports every machine as a fully evaluated NixOS system, so evaluatedConfig fits: the guest is evaluated once, and both the flake output and the hypervisor point at that result.

Extending an already-evaluated guest

If the guest is already evaluated when the host sees it, how does the host add anything? nixpkgs attaches extendModules to every evaluated NixOS system: call it with extra fragments and it re-runs the evaluation with those fragments added, handing back a second, separate system. The original is untouched.

How a credential actually reaches the guest

QEMU has a small channel for handing a virtual machine data at boot, fw_cfg, short for firmware configuration. systemd inside the guest reads its entries and presents them as credentials: short-lived files in a memory-only directory. Upstream builds one QEMU argument per entry in the guest's microvm.credentialFiles setting.

This framework's guest half, modules/microvm-credentials.nix, derives the closed list of credential names from what the machine declares and supplies no values. The host half lives in allod/nexus, which owns nexus.microvm.hostPlaintextRoot: one host directory on a small memory-backed filesystem where the launcher stages each machine's credentials before starting it.

One pinned copy of microvm.nix instead of two

A Nix flake pins the revision of every project it depends on, and because dependencies have dependencies, one project can appear twice at two revisions. This repository reached microvm.nix through allod/vm, and again through allod/nexus, which resolved a second allod/vm; the two copies agreed by coincidence. The one-line inputs.vm.follows = "vm" makes the resolver reuse the first: 28 lock entries become 18, no revision moved. A future update cannot put the host half on a different revision than the guest half.

Why a NixOS assertion does nothing until the machine is built

A NixOS module can register a rule that looks like a check and is not one, and this change's most important test finding is the consequence.

A module can register an assertion: a condition plus a message. Evaluation appends it to a list under config.assertions and stops. One place in nixpkgs — the code producing system.build.toplevel — walks the list and turns failures into an error. Read any other setting and the list is never walked; Nix evaluates lazily, so reading one setting forces only what it needs.

Predict: a check reads settings off a synthetic hypervisor and compares the values it finds. What can that check not notice?

It cannot notice that the configuration could never be built. A failing assertion stays a quiet entry in a list nobody walks, which is what happened here: an earlier version of this check passed on fixtures no host could build, because allod/nexus rejects upstream's default control-socket path and nothing set a valid one. The repair, labelled finding 0, forces system.build.toplevel.drvPath on every positive fixture and reports the failed assertions.

Forcing the build recipe is cheap in time and expensive in memory — each hypervisor fixture holds roughly a gigabyte of live data — which is why the second new check is a separate file.

A test builds a synthetic hypervisor, reads five settings off it, and finds all five correct. One module in that configuration registers an assertion that fails. What does the test report?

  • A. An error naming the assertion, because assertions are raised where they are declared

    Registering an assertion only appends it to a list; nothing inspects that list where it is declared.

  • B. An error, because reading a setting forces the merged configuration and its assertions

    Nix evaluates lazily, and the assertion list is a separate branch that stays uncomputed.

  • C. Five correct settings and no error, on a configuration no host could actually build

    Only the code producing system.build.toplevel walks that list, so a test that never asks for it passes on an unbuildable configuration.

  • D. A type error, because a failing assertion invalidates the surrounding settings

    Type checking and assertions are separate mechanisms; an assertion is ordinary data, not a constraint.

Which guests a hypervisor composes, and the exactly-once fleet rule

A hypervisor composes the microVM host machinery only when its fleet contains a microVM machine, and a new check refuses any fleet where a declared microVM machine is started by other than exactly one host.

Machine facts come from a fourth repository, allod/inventory, as plain data. Each guest entry carries a runtime fact of either libvirt or microvm; hypervisor entries carry none, and inventory rejects one that does. The example fleet is allod-dev and privacy-1 on libvirt plus the hypervisor nexus. Nothing selects microvm.

The hypervisor builder, mkHypervisor, gained an argument microvmGuests: the guests this host starts, keyed by machine name. Its default is computed in three named steps: microvmMachineNames filters inventory data for microVM entries, microvmGuestsFor maps those names to the evaluated configurations this flake exports, and builtins.removeAttrs drops the host's own name. Nothing recurses: the names come from plain data holding no evaluated configuration, and a guest builder reads nothing back from a hypervisor.

Gating on the module list rather than inside a module

With an empty guest set the hypervisor's list of fragments is exactly what it was. Otherwise two are appended: nexus.nixosModules.microvmHost, allod/nexus's policy layer around upstream's host half, and the new join module.

The alternative — importing always and wrapping the contents in a conditional — fails. A conditional defers a value but still produces a definition, and several of these settings are declared only by the gated modules, so a libvirt-only hypervisor gets an unknown-option error. Gating on the list also gives the stronger property: an unchanged module list, an unchanged build recipe.

Evidence

I evaluated system.build.toplevel.drvPath for all four exported configurations at base c02e4e9 and head 59cfc2c. All four match exactly, including the hypervisor. No machine here selects the microVM runtime, so the gate never opens.

Why the free builder argument needed a second check

The microvmGuests argument is deliberately overridable, because no inventory machine declares the microVM runtime and a test has no other way to drive the real builder with a real guest. The cost: builder arguments merge from profile data, so a deployment can hand a hypervisor an empty guest set for a machine inventory calls microvm. Nothing starts it, and every check supplying its own guests stays green.

Predict: the owner rejected "record the gap and move on". Why constrain the exported machine configurations rather than reject an empty guest set in the builder?

Because rejecting an empty guest set would break the seam the tests depend on, and would constrain the wrong object anyway. A hypervisor with no microVM guests is legitimate — every host in this fleet is one today. A deployment consumes the exported machine configurations, so that is where the rule belongs: the new check walks every exported hypervisor, reads back the guest set it composed, and requires the union to be exactly the machines inventory gives the microVM runtime.

The diagnostic states the remediation: such a fleet must name the host it means by passing each hypervisor an explicit guest set. No inventory-level way to express that assignment exists today.

An engineer proposes replacing the list gate with an always-imported module whose body is wrapped in a conditional on the guest set. What happens to the existing libvirt-only hypervisor?

  • A. Nothing changes, because a false condition means the settings are never defined

    A conditional defers the value but still contributes a definition, whether or not the condition holds.

  • B. It fails to evaluate, because settings only the gated modules declare now get definitions

    The gated modules declare several of these settings, so defining them on a host that skipped those modules is an unknown-option error.

  • C. It evaluates with an identical build recipe, since every gated setting keeps its default

    Importing upstream's host half itself adds a system user and group, a command, and memory deduplication.

  • D. It evaluates, and the fleet-wiring check reports the extra modules as an unwired guest

    That check compares guest-set membership against inventory, and a host with extra modules still has an empty guest set.

A deployment adds a second hypervisor and gives neither host an explicit guest set. What does the new rule produce, and why is that the design the change chose?

  • A. Each host starts roughly half the guests, because the default divides the fleet

    The default hands each hypervisor the fleet's microVM machines minus itself, so both guest sets are identical.

  • B. Both hosts start every guest, and the duplicate is caught at runtime by a lock

    Nothing arbitrates between hosts; both would prepare the same state directory and control socket independently.

  • C. Both hosts start every guest and the rule allows it, being written for un-wiring

    The clause is exactly-once rather than at-least-once precisely so this case is covered.

  • D. Evaluation is refused, naming both hosts and the missing guest-to-host fact

    Two hosts starting one machine share its state directory and control socket, which is worse than not starting it at all.

The join module: credential paths, the control socket, and the overlap it refuses

microvmJoinModule does the whole crossing: it reads the host's credential directory setting, builds one file path per credential name the guest declared, re-evaluates the guest with those paths and a control-socket path added, and hands that result to the host as the guest to start.

microvm.nix defaults the socket setting to a bare file name relative to the unit's working directory, putting every machine's socket in one shared state directory. allod/nexus refuses that and requires an absolute path in its own runtime area. Nothing else in the framework sets it, so before this change a hypervisor composing a guest did not evaluate.

One credential, from declaration to QEMU argument

  1. 1. The guest names it and supplies nothing

    For allod-dev the derived list is four names: forge-api-token, forge-https-token, forge-ssh-key, and ssh-host-key. The plain evaluation carries an empty microvm.credentialFiles, and the guest's matching assertion fires only when that set is non-empty, so the plain guest is legal alone.

  2. 2. The host reads its own directory setting

    On the composed hypervisor nexus.microvm.hostPlaintextRoot resolves to its default, /run/allod/microvm, and the join reads that value rather than restating it.

  3. 3. The join builds one path per name

    For ssh-host-key the result is /run/allod/microvm/active/allod-dev/ssh-host-key: host directory, active, machine name, credential name. That shape belongs to allod/nexus, which asserts the same value from its own copy of the setting.

  4. 4. The guest is evaluated a second time

    extendModules re-runs the evaluation with the four paths and the socket path added, and the host stores that result as this guest's evaluatedConfig.

  5. 5. The runner renders the argument, and the host installs that runner

    microvm.nix's QEMU renderer turns each entry into a -fw_cfg argument, and the generated install-microvm-allod-dev service points the host's current symlink at that runner's store path. Because the guest's own system is identical either way, this symlink is the only artifact distinguishing the extended guest from the plain one.

The overlap the join refuses

This change introduces a second fixed host directory, /run/allod/microvm-qmp, holding one control-socket directory per machine. It is a literal rather than a setting, and the owner kept it so: a fixed value cannot be aimed at the wrong place, a guest must not know host filesystem layout, and exporting it from allod/nexus can follow.

That root introduced a hazard. allod/nexus checks one direction — that a machine's control-socket directory is not inside the host's credential directory — and not the reverse, because no fixed socket root existed to check against.

Predict: a deployment sets the credential directory to a path underneath the control-socket root. Which existing checks catch it?

None of them. The value passes the setting's type, which only requires a normalized absolute path under /run/allod, and the normalization assertion. It passes the overlap assertion in allod/nexus too, because that one asks whether the socket directory sits inside the credential directory, and here the nesting runs the other way. The configuration evaluates clean and builds. The damage happens later: the launcher clears each machine's control-socket directory with rm -rf on every start and stop, taking any credential directory nested under it.

The module also reads back over every machine the merged host configuration declares — not only the ones it extended — and requires each one's credential-file keys to equal its declared credential names. allod/nexus cannot state that, because it must not learn the names. Wiring the plain unextended guest trips it by name.

A deployment sets the host credential directory to /run/allod/moved-microvm. Which value ends up in the QEMU argument for the guest allod-dev's ssh-host-key credential?

  • A. /run/allod/moved-microvm/active/allod-dev/ssh-host-key, built from the host setting

    The join interpolates the host setting, so moving the directory moves every path; the check requires no default-directory path to survive.

  • B. /run/allod/microvm/active/allod-dev/ssh-host-key, from the guest's own default

    The guest supplies no values, and its own runtime directory has no bearing on the host paths QEMU is given.

  • C. /run/allod/moved-microvm/active/ssh-host-key, without the machine segment

    The machine segment keeps two guests' credentials apart, and allod/nexus asserts that four-part shape.

  • D. A path under /nix/store, because the value is computed during evaluation

    The value is an ordinary interpolated string, and the guest module rejects a store-prefixed one as world-readable and permanent.

Why does the guard against nesting the credential directory under the control-socket root belong in this repository rather than in allod/nexus, which owns the setting and the launcher that deletes at that path?

  • A. Because assertions only run on the hypervisor, and only this repository builds hypervisors

    Both repositories contribute modules to one hypervisor and their assertions merge into a single list.

  • B. Because a repository may only assert about settings it declares, and this one declares it

    The setting is declared by allod/nexus, and a composing layer is allowed to add rules about settings it reads.

  • C. Because this change introduced the fixed socket root, so the overlap did not exist to check

    The reverse direction became possible only when this change fixed a socket root outside that repository's knowledge, so the party creating the hazard states the rule.

  • D. Because the launcher performing the destructive removal is generated by the join module

    The launcher is generated by allod/nexus; this change contributes only the socket path it is pointed at.

The restart and autostart settings on a wired guest

The join leaves the restart setting at upstream's value and forces the autostart setting off; in both cases the test pins the observable consequence rather than the setting.

When a NixOS machine is rebuilt, a program called switch-to-configuration compares old and new systemd units and decides which services to restart. A unit opts out with a marker, X-RestartIfChanged. The default matters: when the marker is absent, the program restarts the service. Absent and false are one setting on the Nix side and opposite behaviours on the systemd side.

Upstream's autostart setting defaults to on, which makes the host's microvms.target want the unit, so a host rebuild would start the guest. This fleet treats arming a real machine as a deliberate human decision, so the join sets it off. That was measured: deleting the line brings the host's autostart list back holding allod-dev, and a deliberate breakage requires it.

The restart setting changed during review. Upstream computes its default from which shape the host used, and for evaluatedConfig that default is off. The first version of this branch overrode it to on, reasoning that a host rebuild is how a guest gets updated.

Predict: in a fleet where each machine is its own deployment target, what should a host rebuild do to a running guest whose system has changed?

Stage the new one and leave the running one alone. A microVM guest here is deployed the way the existing libvirt machines are: a rebuild inside the guest switches it in place and restarts only the services that changed. A host that restarted every changed guest would reboot machines out from under whoever was working in them. The owner review reversed the original override on that reasoning, and the plan document in allod/strategy was rewritten to match.

So the join sets nothing and takes upstream's off by default — relying on someone else's default, which this repository normally refuses. microvm.nix writes the marker as a two-element list whose first element is empty, and an empty assignment in unit text resets any earlier value, so the pair renders as a reset line then the real value. The check reads that text and requires X-RestartIfChanged=false present and X-RestartIfChanged=true absent.

Evidence

I read the generated unit fragments the check left on this machine. Both positive fixtures render X-RestartIfChanged= followed by X-RestartIfChanged=false; the broken fixture renders the same two lines with true. The Nix reading is kept alongside the text reading so the two cannot drift apart.

A future microvm.nix release stops writing the X-RestartIfChanged key into the generated fragment. The join still sets nothing. What happens on the next host rebuild, and which reading catches it?

  • A. Nothing restarts, because an absent key leaves the previous behaviour in force

    The program restarts a changed unit unless the key says otherwise, so absent is the permissive value.

  • B. Changed guests restart, and only the reading of the generated text catches it

    With the key gone the program restarts each changed guest, while the Nix setting still reports off, so only the literal =false requirement turns this red.

  • C. Changed guests restart, and the Nix setting catches it because the default moved

    The default did not move here; the renderer stopped emitting it, so the setting reads unchanged.

  • D. Evaluation fails, because the join asserts the key is present in the fragment

    The join asserts nothing about the fragment; the requirement lives in the check, which reports a finding.

What the two new checks run, and what they leave untested

The gate now proves that a composed hypervisor is buildable and that its generated text carries the right paths, nothing about a host rebuild or a booted guest; and one of the two new rules walks an empty fleet.

  • 21 stepscounts the machines, checks and passive outputs the gate walks, not assertions inside them
  • 9 breakagescounts deliberate sabotages pinned to their own error text, excluding positive controls
  • 18 lock entriescounts dependency nodes after the redirect, down from 28; no revision moved

The join check builds three hypervisors from the real builders, never by importing the module under test: one at the default credential directory, one at a moved directory, one with no guests. Each is forced to a build recipe first, then read for three generated artifacts no option read can see — the systemd fragment, the service that installs the runner, and the QEMU command line.

That command line is reconstructed rather than built, because building the real launch script would build the whole guest system and its disk image. A change to the renderer's call signature fails the import loudly, and a reconstruction from the wrong configuration is caught by a guard requiring this guest's own disk and kernel parameters. A change in the meaning of the surrounding launch script is left to a later slice that boots a machine.

The fleet rule is a function over plain data — microVM machine names against a table of which host composed which guests — so it can be shown to fail; three deliberate breakages cover its three violations, with two positive controls. The walk itself compares the empty set against the empty set, because this repository declares no microVM machine. Teeth come from the separate deploy flake, which re-runs this suite against real machine data; the author also doctored the check's inputs both ways, saw red, and reverted.

Evidence boundary

Two limits I derived from reading the checks, which the change does not state. The fleet rule compares guest-set membership by name only, so a hypervisor wiring the name beta-dev to some other machine's configuration would satisfy it. And the join check builds its synthetic host sources from the same restated name list it compares them against, so that comparison round-trips its own input; agreement still holds through the set-equality assertion in allod/nexus, but the reading is weaker than it looks.

Where the review changed the design

The worst credible failure is not a wrong credential path: allod/nexus derives its expected value from the host setting and asserts equality, so a wrong-directory extension is refused when a real deployment evaluates. What remains is what this slice cannot observe — whether the system-switching program leaves a changed guest running, and how the launcher and the generated unit interact on a real host. Rollback bounds it: no host was rebuilt, no deployed state is touched, and reverting removes the change.

A reviewer says the nine deliberate breakages make the runtime restart behaviour safe to rely on. What is wrong with that inference?

  • A. Each breakage shows a rule can fail at evaluation; none of them runs a host or a guest

    A deliberate breakage separates a live rule from a permanently green one, but says nothing about behaviour that exists only once systemd runs.

  • B. Nothing is wrong, because the restart breakage pins the generated text both ways

    Pinning the text establishes what the unit will say; how the program then behaves on a live host is a separate claim.

  • C. Nothing is wrong, because every positive fixture is forced to a build recipe and built

    Forcing a build recipe computes the instructions without executing them, so nothing ran.

  • D. The count is too low, and more breakages would establish the runtime claim

    More breakages of the same kind stay evaluation-time; the limit is the kind of witness, not the number.
