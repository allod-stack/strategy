allod/archetypes · pull request #39

Hosts gain a complete path from declared guests to runnable services, without starting any current machine.

A microVM—a small virtual machine launched as a host service—was already describable in guest configuration, but the host never received that finished description. This change connects the two sides, derives temporary credential and control-socket paths, and rejects fleets in which a selected guest has zero or multiple hosts. Accepting it also accepts deliberate coupling: automatic startup and host-rebuild restarts stay off by default, the socket layout becomes a cross-repository contract, and the new checks stop at generated artifacts rather than demonstrating a deployed guest boot.

Decision frame: 2 minutes. Concepts and fleet rules: 16 minutes. Full mechanism and evidence: 28 minutes.

If you read nothing else

Approval accepts the source-level host–guest composition, fixed per-guest socket convention, false-by-default startup and rebuild behavior, exactly-once fleet gate, and shared dependency revisions; it does not certify runtime startup or live credential delivery on a deployed host.

  • What merging changes now

    The source gains a conditional host–guest join, three checks, documentation, and a smaller locked dependency graph. Every current machine fact selects libvirt, the existing virtual-machine runtime, so this join adds no guest service to the four-machine example fleet.

  • What exists afterward

    When inventory selects the microVM runtime, one exported host can receive the guest’s finished configuration and contain its installed runner and service. Credential inputs and a private management socket are derived per guest, while automatic startup remains disabled.

  • What the tests actually prove

    Purpose-built test configurations verify guest selection, configuration extension, exact generated launch arguments, rendered service policy, dependency-lock relationships, and one-and-only-one fleet assignment. The repository gate discovers these checks dynamically.

  • What is still unproven

    No check added here boots a host, starts the generated service, reads live credential bytes inside a guest, or rebuilds a deployed machine. Private deployment repositories are outside this checkout, and the planned nested-host test remains future work.

How one machine definition becomes an extendable configuration

The change does not invent a second guest definition: it selects an already assembled guest, runs the same declarations again with host-known additions, and passes the result to the outside VM service generator named microvm.nix.

The current four exported configurations do not enter the microVM join

A name-to-facts list says what each machine is and, for a guest, which virtual-machine implementation runs it. This list is the machine inventory. The code calls the selected implementation its runtime. The repository publishes finished machine configurations under nixosConfigurations.

Predict what the nexus host gains when no inventory guest selects the microVM runtime

It gains none of the new microVM host machinery. The selected guest set is empty, so mkHypervisor imports neither the allod/nexus module named nexus.nixosModules.microvmHost nor the local microvmJoinModule. No guest service is added to the nexus machine configuration.

Baseline evidence

The locked inventory defines allod-dev and privacy-1 with runtime = "libvirt" and defines nexus without a runtime. flake.nix adds installer separately. The supplied pull-request validation also records identical system.build.toplevel.drvPath values—the identifiers of the final system build recipes—for all four exports before and after this change.

NixOS evaluation turns declarations into a finished configuration

NixOS describes a machine with declarative fragments that state desired settings, such as a hostname, a user, or a service, instead of issuing installation commands. These fragments are modules. Different modules can declare allowed settings, provide defaults, set values, and attach rejection rules called assertions.

The calculation that merges those fragments and checks how their declarations fit together is evaluation. Nixpkgs—the source collection that supplies NixOS and its programming library—provides the function nixosSystem for that calculation. nixosSystem takes a target platform and a module list. Its result is a configuration object whose config field contains the merged values and build instructions.

In this repository, machineConfigurations walks the inventory. For each name it chooses an archetype builder—mkDevVm, mkPrivacyVm, or mkHypervisor—from the machine type. Each builder assembles its module list and calls nixosSystem. The public nixosConfigurations output is then the resulting machineConfigurations map plus the separately evaluated installer.

Evaluation is not execution

A value called an evaluated configuration is a computed plan for a machine. That does not show the machine was built, started, or observed running.

The host extends the selected guest instead of describing it again

Consider complete hypothetical deployment data whose inventory contains guest-a with type dev and runtime microvm. machineConfigurations.guest-a is first produced normally by mkDevVm and nixosSystem. The finished guest configuration before a particular host contributes host-only paths is the standalone guest.

The configuration object carries a function that creates a fresh evaluation from the original module list plus additional modules. That function is extendModules. The standalone guest is not edited in place. In this change, the joining module named microvmJoinModule calls guest.extendModules to add the credential-file map and control-socket path known by the host.

Why extend the finished guest instead of constructing a second guest on the host?

Extension keeps one source of truth. The added host values pass through the guest's existing option declarations, value checks, defaults, and assertions. A second hand-built guest could omit a module or reproduce a rule differently, leaving the exported guest and the started guest with different meanings.

This choice buys consistency, not automatic correctness. The added module still participates in ordinary NixOS merging. An unknown setting, a value of the wrong kind, a failed assertion, or two incompatible values can reject the result. Extension also creates another configuration evaluation and therefore consumes evaluation memory; the empty-guest gate avoids that cost for the current fleet. The safety property is narrower: the join goes through the same evaluator as the original guest rather than bypassing it with an unchecked object patch.

microvm.nix has a host-side option for a guest configuration that has already gone through evaluation. That option is named evaluatedConfig. microvmJoinModule assigns the extended object to microvm.vms.guest-a.evaluatedConfig. microvm.nix then reads that object's merged guest settings and its runner—the launch program built for that guest—instead of evaluating a separate guest specification. The standalone export still exists unchanged; the host explicitly receives the extended result.

The host reads guests in only one direction

The source can look circular: the selected-guest collection named fleetMicrovmGuests refers to machineConfigurations, while machineConfigurations also contains the nexus host that receives fleetMicrovmGuests. Nix, the language and evaluator used to assemble NixOS, computes a named value only when another demanded value needs it. This behavior is lazy evaluation. Laziness alone does not make every circle safe; the direction of the reads matters.

Why does selecting a guest configuration not force the host to read itself?

The runtime filter named microvmMachineNames takes names from the inventory and selects only entries whose runtime is microvm. A hypervisor has no runtime, and mkHypervisor also removes its own name. The mapping function named microvmGuestsFor then reads only the selected guest keys from machineConfigurations. The guest builders never read a hypervisor configuration, so the reference runs from host to finished guest and not back again.

For guest-a, the complete trace is therefore: inventory selects guest-a; machineConfigurations.guest-a evaluates its ordinary guest modules; microvmGuestsFor hands that object to mkHypervisor; microvmJoinModule reevaluates it with host-known values; and the exported host contains the extended object at microvm.vms.guest-a.evaluatedConfig. With the current empty selection, that trace stops before the host imports any microVM module.

How the host installs, starts, and restages a guest

The generated host plan installs a wired guest's runner but deliberately leaves the guest stopped: automatic startup is disabled, an unexpected process exit still causes a retry, and a host rebuild stages the next runner without rebooting the running guest.

Installation, startup, and restart are separate decisions

Once microvm.nix receives evaluatedConfig, it builds a runner: a directory of launch programs for that exact guest configuration. The host does not execute the runner directly from an arbitrary build result. A host service named install-microvm-<name> points the guest's current link at that runner, and a second service named microvm@<name>.service launches whatever current names.

The host's service manager is systemd. A systemd unit is a set of instructions for one service or for a named group of services. microvm.nix defines microvm@.service as a reusable unit template; the text after @ selects an instance such as microvm@guest-a.service. It also defines microvms.target, a grouping unit reached during ordinary multi-user host startup.

The switch that controls membership in the automatic-start list is autostart. microvm.nix normally sets it to true. The join overrides it with autostart = false for every guest created by microvmJoinModule.

If guest-a has autostart = false, which part disappears: its runner, its service definition, or only the automatic request to start it?

Only the automatic start request disappears. microvm.nix still generates install-microvm-guest-a and microvm@guest-a.service. The install service still stages the runner under current, but microvms.target does not ask systemd to start the guest process.

Because autostart controls only that request, wiring makes a guest available for an explicit start; wiring alone does not boot it.

The process-recovery row belongs to systemd itself. The pinned microvm.nix template says Restart=always and RestartSec=5s. allod/nexus replaces the template's launch command with its credential-preparing launcher, but it leaves those recovery instructions intact. If QEMU—the guest process—exits unexpectedly, systemd waits five seconds and runs the launcher again. That buys recovery from a short-lived failure, at the cost of repeated launch attempts when a persistent fault remains. A guest that has never started remains stopped, and a deliberate systemd stop does not trigger the retry.

Two similarly named restart controls

Restart=always tells systemd what to do after a running process exits. X-RestartIfChanged=false tells the NixOS host-activation program what to do when a newly built host configuration changes a service definition. The first remains enabled; the second prevents a rebuild-driven guest reboot.

Automatic startup is a separate human opt-in

Why does the join reject microvm.nix's automatic-start default instead of treating a declared guest as permission to boot it?

The recorded owner decision separates declaring a real machine from arming it. Keeping microvm.nix's true default would let the act of wiring a guest make microvms.target request its first boot during host startup or activation. Setting false requires a separate deployment choice before that process can start automatically.

The benefit is a rollout that stays stopped unless someone explicitly enables it: composition, evaluation, and installation can land before a machine is allowed to run. The cost is operational work. A real deployment that should survive host reboots must override autostart to true; otherwise an operator must start it manually after each host boot.

checks/microvm-host-join.nix proves that such an override is technically possible. Its test module uses lib.mkForce, a Nix module marker that makes one declared value win over ordinary declarations, and observes its selected fixture guest entering microvm.autostart. That is evidence that the setting can be changed, not a deployment policy.

Unresolved operator interface

microvm.nix supplies the underlying autostart option, but this pull request adds no repository-specific opt-in option, documented deployment recipe, or sanctioned location for setting it. The review record says a deployment opts in and the check demonstrates lib.mkForce, but it does not establish that test technique as the operator-facing policy. Approval therefore accepts the safe default while leaving the governance interface to later work.

A host rebuild changes the next start, not the current process

Applying a newly built NixOS host configuration is host activation; its program is named switch-to-configuration. The program compares the old and new systemd units and decides which changed services to stop, start, or skip. microvm.nix adds a small per-guest unit fragment, called a drop-in, to the shared microvm@.service template. That fragment contains the NixOS-only instruction X-RestartIfChanged.

microvm.nix computes restartIfChanged from the shape used to supply the guest. Its default is true when the host asks microvm.nix to evaluate a guest module through microvm.vms.<name>.config. The join instead supplies the already evaluated object through evaluatedConfig, so microvm.vms.<name>.config is empty and the microvm.nix default becomes false. The join deliberately leaves that default in place.

A running guest uses runner A. A host rebuild stages runner B while X-RestartIfChanged=false. Which runner is used now, and which is used after the next start?

The process already running from runner A stays alive. The install service moves current to runner B, while switch-to-configuration skips the changed guest service. The next start reads current and uses runner B. That next start can be an explicit operator restart or the retry that follows an unexpected exit of the process from runner A.

Host activation with a changed guest

  1. 1. Build runner B

    The new host plan refers to the runner produced from the changed extended guest.

  2. 2. Restage current

    install-microvm-<name> replaces the link to runner A with a link to runner B. Updating that next-start link without changing the live process is restaging.

  3. 3. Skip the running service

    switch-to-configuration reads X-RestartIfChanged=false and does not reboot the guest merely because its generated unit changed.

  4. 4. Use runner B on the next start

    An explicit restart or a later process-failure retry follows current and launches the staged version.

This policy buys continuity for a guest that is being used while its host changes. It costs an immediate match between staged and running versions: the files prepared for the next boot and the process running now can represent different guest versions. The recorded owner decision accepts that interval because this fleet updates each guest in place as its own deployment target, through the allod/nexus tool named rebuild-vm-from-host, rather than using a host rebuild as the guest-update operation.

Why does the check require the rendered line instead of checking only that the Nix value is false?

switch-to-configuration treats a missing X-RestartIfChanged line as true. A source-level value of false would not protect the lifecycle if a future microvm.nix stopped writing the line. The check therefore requires X-RestartIfChanged=false, rejects =true, and uses a forced-true fixture to prove that its text reader can observe the opposite result.

Source and generated-artifact evidence

The pinned microvm.nix host options define autostart = true and make restartIfChanged false for the evaluatedConfig shape. Its host module generates the install unit, target relationships, five-second process retry, and per-instance drop-in. checks/microvm-host-join.nix observes the joined guest's false values, the empty automatic-start list, the extended runner path inside the install script, and the exact rendered X-RestartIfChanged=false line. These witnesses establish the generated plan. They do not observe a live guest retaining its process identity across an actual host rebuild.

Credential paths and per-guest control-socket isolation

For each selected guest, the join derives temporary host credential paths and a separate QEMU management-socket directory from the guest name; allod/nexus prepares and removes those paths for one service run, while checks forbid either runtime root from containing the other.

One credential keeps its name while its address changes at each boundary

Suppose a selected guest named guest-a declares the credential name ssh-host-key. The declaration names what the guest expects; it contains no secret bytes and no host file location. A deployment separately gives allod/nexus a source path under nexus.microvm.machines.guest-a.credentialSources. The source file remains deployment-owned.

allod/nexus provides a memory-backed host directory for plaintext credentials. This directory is the hostPlaintextRoot. Its default is /run/allod/microvm. allod/nexus mounts that directory as a bounded 16 MiB temporary filesystem with swapping disabled, mode 0700, and root ownership. The new microvmJoinModule reads the evaluated value rather than repeating the default.

Predict the host path for guest-a's ssh-host-key when hostPlaintextRoot is /run/allod/microvm

The path is /run/allod/microvm/active/guest-a/ssh-host-key. The rule is the evaluated host root, then active, then the guest name, then the credential name.

The ssh-host-key crossing for guest-a

  1. 1. The join derives a host address

    microvmJoinModule extends the guest with microvm.credentialFiles.ssh-host-key = "/run/allod/microvm/active/guest-a/ssh-host-key". This value is ordinary text naming a runtime file. It is not a Nix path value that would copy the file into the world-readable Nix store.

  2. 2. The host installs the extended runner

    microvm.nix builds the launch program named declaredRunner from the extended guest, so its command contains the derived address. The install-microvm-guest-a service stages this runner rather than the standalone guest's runner.

  3. 3. allod/nexus prepares bytes for one start

    When microvm@guest-a.service starts, the allod/nexus launcher copies the deployment source into a root-only staging directory, sets the file to mode 0400 for the dedicated microvm-guest-a process account, and publishes the completed guest directory with one rename.

  4. 4. QEMU exposes a firmware credential

    microvm.nix renders -fw_cfg name=opt/io.systemd.credentials/ssh-host-key,file=/run/allod/microvm/active/guest-a/ssh-host-key. fw_cfg is QEMU's channel for exposing host-supplied data as firmware entries inside the guest. The command contains a file path, not the credential bytes.

  5. 5. The guest gives the credential to its consumer

    During boot, systemd—the guest's service manager—imports the firmware entry under the same name. For this credential, the SSH service reads /run/credentials/sshd.service/ssh-host-key. Other declared credentials are turned into consumer files under the guest's separate temporary root, /run/allod/credentials.

The host path and the guest paths are intentionally different. /run/allod/microvm/active/guest-a/ssh-host-key exists in the host's runtime tree and is made visible to QEMU at the same absolute address inside QEMU's private filesystem view. /run/credentials/sshd.service/ssh-host-key and /run/allod/credentials exist inside the guest. Reusing the word credential does not make these one shared directory.

If the host root moves to /run/allod/moved-microvm, which parts of this trace move with it?

Every microvm.credentialFiles value moves, and each QEMU file= argument moves with it. The credential name stays ssh-host-key, the guest still receives that name through systemd, and the management socket remains under /run/allod/microvm-qmp. This check evaluates the moved-root case and rejects any surviving default-root argument.

Generated-command evidence stops before delivery

checks/microvm-host-join.nix proves the exact map, the extended runner selected by the install service, and the reconstructed fw_cfg arguments at the default and moved roots. The check neither runs this joined launcher nor shows the guest reading the bytes. The existing checks/microvm-sshd-boot.nix boots neighboring test machines and proves that this fw_cfg form reaches systemd and SSH, but it does not exercise microvmJoinModule.

Each guest receives a private QEMU management directory

QEMU accepts management commands over the QEMU Machine Protocol (QMP). On this host, QMP uses a Unix socket: a filesystem entry through which a local program can ask QEMU to perform operations such as graceful shutdown. microvm.nix reads the socket address from the guest setting named microvm.socket and passes it to QEMU.

microvm.nix normally defaults microvm.socket to a relative name such as guest-a.sock. A relative name is resolved from the service's working directory, so multiple guests place management state in the shared microvm.nix state tree. allod/nexus rejects that default because its launcher needs one absolute, host-controlled QMP directory for each guest.

Why not give guest-a and guest-b different socket filenames in one shared writable directory?

A different filename does not isolate the directory. The process account that can create its own socket in a shared writable directory can also rename or unlink a sibling's socket. allod/nexus therefore rejects duplicate QMP directories, not merely duplicate full socket paths.

The join replaces the microvm.nix default with /run/allod/microvm-qmp/guest-a/control.sock. A second guest named guest-b receives /run/allod/microvm-qmp/guest-b/control.sock. allod/nexus creates each guest directory as root and that guest's dedicated process group, exposes only that directory read-write inside the guest's QEMU process environment, clears stale contents before launch, and removes it after stop. This buys a predictable cleanup target and prevents one QEMU process account from managing a sibling's socket.

The fixed root is the deliberate value microvmQmpSocketRoot = "/run/allod/microvm-qmp". A fixed value removes a deployment setting that could point cleanup at the wrong tree. Its cost is a cross-repository convention: allod/archetypes constructs the address, microvm.nix renders it, and allod/nexus creates and removes the directory.

Both runtime roots are rejected when either one contains the other

If the credential root and QMP root have different final names, is that enough to make cleanup safe?

No. Directory containment is directional. A check that rejects a QMP directory inside the credential root says nothing about a credential root placed inside the QMP tree. Cleanup is safe only when neither runtime tree contains the other.

The reverse-direction assertion is intentionally broad. For example, /run/allod/microvm-qmp/guest-a/creds would sit below the directory that the guest-a launcher recursively clears before start and after stop. Rather than prove that a chosen child such as /run/allod/microvm-qmp/creds is currently a sibling of every guest directory, the assertion reserves the entire QMP root for QMP state. This costs the ability to place the plaintext mount in a presently unused QMP-root child. It buys safety across guest renames and additions without another placement rule.

What the overlap sabotage proves

The permanent sabotage sets hostPlaintextRoot to /run/allod/microvm-qmp/creds and proves that the broad assertion rejects it with the intended message. That particular child is a sibling of the current fixture guest's QMP directory, so the sabotage does not itself demonstrate destructive traversal. The destructive case follows from the cleanup code when the plaintext root lies below a directory that is actually removed, such as /run/allod/microvm-qmp/guest-a/creds. No test in this pull request runs either cleanup path.

The fixed socket convention belongs to the join for now

Why does allod/archetypes set a host QMP path inside the extended guest instead of making the standalone guest choose one?

The standalone guest does not know which host will run it or where that host keeps temporary state. microvm.nix requires the host address in the guest configuration because the guest's runner renders QEMU's command. The allod/archetypes join is the point where the finished guest and the selected host meet, so it can add the host-only address without making the reusable guest definition know host layout.

The owner review accepted this placement and the fixed value. It also recorded a defensible future refactor: allod/nexus could export the path constructor beside the launcher that removes the resulting directory. That would reduce the distance between the convention and its destructive consumer. It is not implemented here, and the recorded decision does not require it before merge.

Isolation evidence and remaining contract risk

checks/microvm-host-join.nix requires the exact /run/allod/microvm-qmp/<guest>/control.sock value and forces configurations with both safe roots and the rejected reverse placement. The pinned allod/nexus module separately rejects relative sockets, shared QMP directories, and QMP directories inside its plaintext root. These checks establish the configured boundary. Future changes that move path ownership between allod/archetypes and allod/nexus must move both containment directions and their tests together; source checks cannot prove that live recursive cleanup touched only the intended directories.

Exactly one exported host must own every selected guest

The new fleet gate compares inventory with the finished host configurations: every machine that selects the microVM runtime must appear under exactly one exported hypervisor, no other machine may appear there, and a fleet with no selected guests passes only after the gate has inspected at least one hypervisor.

Host ownership means presence in the finished host configuration

A hypervisor is a host machine that runs virtual machines. In this rule, saying that a hypervisor “owns” guest-a has one precise meaning: guest-a is a key in that exported host's finished config.microvm.vms map. It does not mean that inventory contains an ownership label; no such label is added by this pull request.

The check named checks/microvm-fleet-wiring.nix derives the required side with microvmMachineNames machines. That function selects every inventory machine whose runtime is microvm. It derives the actual side with composedGuestsOf, which reads the guest-name keys from each inventory machine whose type is hypervisor. If a host has no microvm setting tree at all, composedGuestsOf deliberately reports an empty list instead of failing on a missing setting.

For one selected guest, the number of exported hypervisors containing that name is its fleet wiring cardinality. The accepted number is exactly one. A second, reverse comparison rejects host entries that inventory did not select for the microVM runtime.

If inventory selects guest-a and both host-a and host-b contain it, has the fleet satisfied the rule twice?

No. The fleet wiring cardinality is two, so the check rejects the fleet. “At least one host” would prevent an abandoned guest but still allow two hosts to claim the same logical machine. The rule requires one host, not one or more hosts.

Valid, missing, duplicate, unexpected, and empty assignments

The missing case catches a selected guest whose host received an empty guest map. The duplicate case prevents two exported plans from starting the same logical guest; the check's diagnostic names the shared state-directory and QMP-socket identity as the danger. The unexpected case catches stale or hand-written host wiring after inventory has changed a machine to another runtime. The valid empty case preserves the current libvirt-only fleet without importing microvm.nix into its host.

An empty selected set is not the same as inspecting no hosts

A fleet with one hypervisor and no microVM-selected machines has a meaningful result: that host must compose no guests. A fleet with no hypervisor gives the check no host output to read. fleetFindings rejects the latter with “the fleet exports no hypervisor, so this check walked nothing.” This guard also rejects an intentionally guestless inventory with no host; the repository accepts that restriction so removing or renaming its only hypervisor cannot turn the fleet check into a silent pass.

The gate reads exported results because builder inputs can be replaced

mkHypervisor receives a name-to-configuration map called microvmGuests. Its default is fleetMicrovmGuests, which maps all microVM-selected inventory names to their existing entries in machineConfigurations, except that a host removes its own name. The builder then turns those inputs into the host's config.microvm.vms output.

Why not validate only the default fleetMicrovmGuests map before calling mkHypervisor?

The default is not necessarily what an exported host receives. machineConfigurations merges the ordinary builder arguments with per-machine profileData and then with settings from machine.profile; later values replace earlier values with the same name. Either source can therefore replace microvmGuests, including with an empty map. A check of the default would remain green while the exported host contained no guest. Reading config.microvm.vms checks the result that a deployment actually consumes.

This placement deliberately keeps microvmGuests free for test fixtures while closing the production override risk at the output. The cost is that a bad assignment survives until the fleet check evaluates all exported hosts; mkHypervisor by itself still accepts the input. The benefit is that test code can construct focused host fixtures without weakening the rule applied to nixosConfigurations.

A second hypervisor requires an explicit non-overlapping assignment

If the fleet adds host-b and changes no assignment settings, will mkHypervisor split guests between the two hosts?

No. The default gives every hypervisor the complete fleetMicrovmGuests map, minus only the host's own name. Both host-a and host-b therefore receive every ordinary selected guest. The fleet check sees cardinality two for each guest and rejects the outputs.

The exactly-once choice buys a loud failure instead of silently choosing a host or allowing two hosts to claim one guest. Its immediate cost is that a deployment cannot safely add a second hypervisor and leave the current broad default unchanged. The deployment must replace each host's microvmGuests input so the finished maps form a non-overlapping split: every selected guest in one map, no selected guest in two maps.

The available input is concrete but the policy around it is not. microvmGuests is keyed by guest name and its values are complete evaluated guest configurations. The existing profileData and machine.profile merge path can replace that builder input. It adds no permanent guest-host inventory field, structured assignment format, or documented recipe for a multi-host split through those profile sources.

The validator does not choose placement

checks/microvm-fleet-wiring.nix can say that a proposed assignment is complete and non-overlapping. It cannot decide whether guest-a belongs on host-a or host-b. Approval therefore accepts a strong rejection rule and the current builder override point, while leaving the durable multi-hypervisor assignment interface undocumented.

Evidence for the public empty fleet and all assignment outcomes

The current inventory has one hypervisor, nexus, and no machine whose runtime is microvm. The production comparison is therefore an empty required set against an empty nexus guest set. This proves that composedGuestsOf safely reads a host with no microvm setting tree, but it does not exercise a real selected guest.

At the rule level, the check compensates. Three deliberately invalid inputs require diagnostics for a missing guest, a guest on two hosts, and an unexpected guest. Two accepted controls require no diagnostic for an exactly-once assignment and for a fleet with no selected guest. Separate reader controls prove that composedGuestsOf sees a populated map, an explicitly empty map, and an absent microvm tree. These cases show that the comparison can distinguish every listed outcome; they do not show a private fleet passing.

External deployment provenance

The pull-request discussion says deployment flakes redirect the public inventory and profiles inputs to private repositories and rerun this check, making the selected set nonempty there. Those private flakes are not present in this checkout. The public evidence cannot establish that every deployment exposes this check, runs it, or supplies the intended future host assignment.

One root pin now supplies both sides of the VM contract

allod/archetypes now selects one exact allod/vm source revision at its outermost project level, and a new redirection makes allod/nexus reuse it. Because that allod/vm source supplies both microvm.nix module roles, the host and guest can no longer drift onto separate revisions inside allod/archetypes. Neither selected revision changes, but future upgrades move both roles together.

Flake inputs form a locked dependency graph

A Nix project description that names its external sources and exported results is a flake. The named external sources are its inputs. An input can declare inputs of its own, so Nix sees a graph: each source is a node, and each “uses this input” relationship is an edge. The outermost allod/archetypes flake is the root of this graph. flake.nix declares the relationships; flake.lock records the exact source selected for every node reachable from that root.

Fixing an input to one exact source revision—one source-control commit—is a pin. Before this change, allod/archetypes had a root input named vm, while its allod/nexus input also declared a nested input named vm. The root vm supplies vm.nixosModules.microvmGuest to the guest builders. The nested vm supplies vm.nixosModules.microvmHost to allod/nexus. Each vm node in turn selects microvm.nix.

If both old vm nodes name the same commit, are they already one pin?

No. They are separate graph nodes reached through separate edges. They happened to select the same commit at the base revision, but either edge could be updated later without moving the other. Each node also carried its own nested dependency branch, including a separate microvm.nix node.

Which ten lock nodes disappear with the duplicate branch

The regenerated lock removes vm_2, microvm_2, agenix_2, darwin_2, disko_2, home-manager_3, home-manager_4, nixpkgs-unstable_2, spectrum_2, and systems_2. These are lock-graph labels, not ten package removals from a machine. Every locked source record that remains under the same label is unchanged between the base and head locks.

The allod/nexus vm input now reuses the root vm source

A rule that tells a nested input to reuse a node already selected elsewhere in the enclosing flake is an input-following rule, written with follows. Inside the allod/nexus input declaration, this pull request adds inputs.vm.follows = "vm". The left side names allod/nexus's requested vm input. The right side names allod/archetypes' root vm input.

Why redirect allod/nexus instead of keeping two equal revisions and checking that they stay equal?

The redirect removes the independent choice that creates drift. A comparison can report disagreement after two revisions separate; follows makes both consumers resolve through one choice in the first place. Keeping two branches would also preserve duplicate nested lock entries and require every update to coordinate both pins manually.

There is no new direct microvm.follows line in allod/archetypes. The microvm.nix unification is a consequence of sharing vm: the pinned allod/vm flake owns one microvm input, imports its guest module for microvmGuest, and exposes its host module under allod/vm's own microvmHost output. Exposing another project's value under a local output is a re-export. allod/nexus imports that re-export. Once allod/archetypes and allod/nexus share allod/vm, they necessarily share its microvm.nix node as well.

This buys consistency at the interface joined by this pull request. The guest's settings and runner are interpreted by host machinery from the same microvm.nix revision, rather than by independently updatable implementations that currently agree by coincidence. Sharing a revision does not prove that microvm.nix is correct, but it removes mismatched dependency revisions as one failure mode.

The root vm pin now owns future upgrades for both sides

What happens to allod/nexus when allod/archetypes later advances its root vm pin?

allod/nexus receives that same new allod/vm revision when allod/archetypes is evaluated. allod/vm's microvmGuest wrapper and microvmHost re-export move together. If the new allod/vm revision changes its microvm.nix selection, both roles receive that changed microvm.nix revision together as well.

The benefit is one reviewable upgrade point for a two-sided contract. The cost is lost independence: allod/archetypes can no longer keep allod/nexus on one nested allod/vm revision while guest builders use another. A root vm update therefore has a wider test obligation. It must rerun the guest checks, host-join checks, generated-command checks, and available lifecycle checks that cover both roles, rather than treating one side as untouched. A nested-host test remains the missing runtime witness.

Policy scope

Contract 1a and the source comments record this shared-revision policy for allod/archetypes. The new follows line does not rewrite allod/nexus's own flake or impose one update policy on every repository that consumes allod/nexus. Another top-level consumer still decides whether its allod/nexus input follows a root vm.

It also requires exactly one distinct allod/vm revision and one distinct microvm.nix revision in the lock data. A doctored lock points allod/nexus at vm_2 and gives the two allod/vm and microvm.nix branches different revisions; the check requires all three defects to be reported.

They also cover the Nix command-line option named --override-input, which temporarily replaces an input for one evaluation without editing the checked-in lock.

Knowledge check for the host–guest join

Apply the composition, path, lifecycle, fleet, isolation, dependency, and evidence rules to new cases. Each answer explains the rule that governs the result.

A selected guest already exists as machineConfigurations.guest-a, and its host must add runtime paths without creating a competing guest definition. Which composition preserves that requirement?

  • A. Build a second guest from host-only modules and register that new guest as evaluatedConfig

    Incorrect. A second construction can omit or reinterpret declarations from the exported standalone guest, creating two sources of truth.

  • B. Patch the standalone guest's merged values directly and register the patched map as evaluatedConfig

    Incorrect. Direct map changes bypass the guest's module declarations, merge rules, type checks, and assertions.

  • C. Call guest.extendModules with the host values and register the resulting object as evaluatedConfig

    Correct. extendModules reevaluates the original module list with the host additions, preserving one guest definition and its checks.

  • D. Register the standalone guest unchanged and let the launcher append host paths after selecting its runner

    Incorrect. The guest runner renders the QEMU arguments, so the host-derived paths must enter the guest evaluation before that runner is built.

A guest named blue declares ssh-host-key, and its host changes hostPlaintextRoot to /run/tenant-vm. Which final path and runner combination should appear?

  • A. The extended runner uses /run/tenant-vm/active/blue/ssh-host-key for fw_cfg and /run/allod/microvm-qmp/blue/control.sock for QMP

    Correct. The evaluated plaintext root moves the credential map and QEMU file argument, while the fixed QMP root remains separate.

  • B. The extended runner uses /run/tenant-vm/active/blue/ssh-host-key for fw_cfg and /run/tenant-vm/blue/control.sock for QMP

    Incorrect. Moving hostPlaintextRoot changes credential addresses only; the QMP socket stays below the fixed QMP root.

  • C. The standalone runner uses /run/tenant-vm/active/blue/ssh-host-key for fw_cfg and /run/allod/microvm-qmp/blue/control.sock for QMP

    Incorrect. The changed paths are injected by guest extension, so the install service must stage the distinct extended runner.

  • D. The extended runner uses /run/credentials/sshd.service/ssh-host-key for fw_cfg and /run/allod/microvm-qmp/blue/control.sock for QMP

    Incorrect. QEMU opens the prepared host path; the guest-side systemd credential address exists only after the firmware entry crosses into the guest.

A joined guest has autostart = false. An operator starts runner A, a host activation stages runner B with X-RestartIfChanged=false, and runner A later exits unexpectedly. What happens?

  • A. Host startup launches runner A, activation keeps it running, and the later exit launches runner B

    Incorrect. The install service can stage runner A, but autostart = false prevents host startup from requesting the guest process.

  • B. The operator launches runner A, activation immediately restarts it as runner B, and later exits keep retrying B

    Incorrect. Restart=always governs process exits; it does not override X-RestartIfChanged=false during host activation.

  • C. The operator launches runner A, activation leaves it running, and the later exit leaves the guest stopped

    Incorrect. The false activation marker prevents a rebuild-driven reboot, while systemd's separate process-recovery rule still retries an unexpected exit.

  • D. The operator launches runner A, activation leaves it running while staging B, and the later exit retries with runner B

    Correct. Activation moves current to B without replacing the live process, and the later recovery attempt follows that updated link.

A proposed host gives every guest a different QMP filename in one shared writable directory and puts hostPlaintextRoot at /run/allod/microvm-qmp/cache. Which revision satisfies the isolation rules?

    Incorrect. A process with write access to the shared directory can alter sibling sockets, and the credential root still lies inside the QMP tree.

  • B. Move the credential root outside the QMP tree but keep every guest's socket in the shared writable directory
