allod/archetypes · pull request #43

Three agent instruction files and one system prompt now render from one table and one template, and a symlink collision stops the rebuild instead of passing silently

The module that sets up a developer virtual machine used to hand-write three near-identical blocks of instruction text and a fourth, differently worded prompt. It now keeps one three-row table of coding agents and one template for the sentence telling an agent to read its memory files, so the next rebuild gives every agent the same mandatory-read wording over absolute paths. Accepting it means new instruction text reaches every agent session on those machines at once, and one activation line that used to succeed wrongly now fails loudly.

Summary: 1 minute. Background concepts: 5 minutes. Full mechanism and receipts: 12 minutes.

If you read nothing else

Approving this accepts rewritten agent-facing instruction text on every developer virtual machine at its next rebuild, and accepts that a real directory at one symlink path will now stop that rebuild rather than be worked around; nothing changes on any non-developer machine.

  • What merging changes now

    On the next rebuild, three files that coding agents read at startup are rewritten from one template, and the extra prompt text given to Claude Code lists its two memory files by full path instead of relative to the working directory.

  • What exists afterward

    One table names the three coding agents; one template writes the mandatory-read sentence for all four artifacts. The instruction to read topic files no longer appears in this repository at all: allod/memory states it once, in its own memory.md.

  • What the tests actually prove

    A build-time check reads the exact activation text and the exact prompt file that ship, and refuses to build unless both name the right files, carry the framing once per agent, keep the strict symlink flag, and never mention topic files. Building it succeeds at this commit.

  • What is still unproven

    Nothing verifies that the files these instructions name exist on a running machine, or that a machine's copy of allod/memory is new enough to carry the topic-file rule that this change stopped stating. A Claude Code session now receives the framing twice over four files; that duplication was not tested.

  • How to reject or roll back

    Revert the single commit and rebuild. Every artifact here is regenerated from scratch on each activation, so the previous text returns with nothing left behind.

What you can do after reading

Six abilities bound this report; every section, figure, and quiz item below serves at least one of them.

  1. You can predict the exact bytes of one rewritten instruction file — its header line, the mandatory-read sentence, the blank line, and the numbered full paths, with nothing indented — from the three-row table and the one template alone.
  2. Given the strict symlink flag, you can decide whether it is safe to merge, because you can say what a failure on that line aborts and which later setup work never runs.
  3. Tracing the check backwards, you can explain how it reaches the actual prompt file the shell alias delivers, and why that is the shipped artifact rather than a copy of it.
  4. You can explain why the topic-file reading rule was deleted here, name the one file that now states it, and name the condition under which a machine would see it from neither source.
  5. Shown a regression — the strict flag dropped, a topic-file sentence put back, a fourth agent added to the table — you can say which error message fires, and name regressions the check would miss entirely.
  6. The blast radius becomes predictable: which machines rebuild differently, which agents see new instructions, and what a revert restores without residue.

Nix indented strings and quoted heredocs

Two independent rules — one from Nix, one from the shell — decide the indentation of the shipped instruction files, and both put every line at the left margin even though the source is indented four spaces.

Nix is both a package manager and the small language it is configured in. A machine's configuration is a program in that language, and evaluating it produces, among other things, a plain shell script the machine runs to set itself up. This change is entirely about what text that program produces.

Nix has a multi-line string form written between two pairs of single quotes. It is called an indented string, and the name is the behavior: Nix finds the smallest leading whitespace shared by the lines inside and removes exactly that much from each. Source indented four spaces to sit inside a function body therefore produces text with no indentation.

Inside any Nix string you can splice in a computed value between a dollar sign and braces. Nix calls this interpolation, and the rule that matters is what it does not do: it inserts the value exactly as it is. Newlines go in untouched, and lines after the first do not inherit the indentation of the splice.

Predict where the numbered lines land before reading the answer

A multi-line value is spliced into a source line indented four spaces. Its first line ends up at the left margin, because those four spaces are part of the shared indentation Nix strips. Every later line was never indented at all. Both rules point the same way: the whole block sits flush left.

The second rule comes from the shell. A heredoc feeds literal text to a command: the command, then two less-than signs and a word, then the lines of text, then that word alone on a line to end the block. Here the command is cat writing to a file, and the word is POINTER.

The word is written in single quotes, as <<'POINTER', and that quoting makes the shell copy the lines through byte for byte, expanding no dollar signs and running no backticks. That is what makes it safe to write file paths wrapped in backticks, which is what the instruction text does. The shell also strips nothing from the front of the lines — the dash form would strip leading tabs, and this is not that form.

Evidence

Evaluating this function on its own with the real inputs produces a block whose lines are all flush left, and the file on disk is exactly five lines with a final newline. The same text appears verbatim inside a Home Manager generation already built on the machine that produced this report — a second, independent witness to the same bytes.

The Home Manager activation script and the order of its entries

Everything a rebuild does to a user's home runs as one bash script that stops at the first unguarded command failure, so the question "is this line allowed to fail?" is really the question "what comes after it?".

Home Manager is a companion project to NixOS that owns one user account's home directory: which programs that user has, what their configuration files contain, and small setup steps that cannot be expressed as a file. That last category is called activation. When a machine rebuilds, Home Manager generates a single bash script and runs it.

Modules contribute named chunks to that script, called activation entries. An entry declares only what it must run after — this module uses lib.hm.dag.entryAfter to place its entry, llmMemoryLinks, after the marker writeBoundary, past which it is safe to write into the home directory. Home Manager flattens those constraints into one linear order. The structure is a directed acyclic graph; the consequence is that entries end up concatenated into one script, each seeing the effects of every entry above it.

The generated script begins with set -eu and set -o pipefail. The first is what matters: any unguarded command that exits non-zero ends the entire script there. Nothing below runs — not the rest of its own entry, not any later entry.

The order in that diagram is not a guess. A Home Manager generation built for this deployment's developer machine sorts its entries alphabetically after the shared boundary, and the four that follow llmMemoryLinks are onFilesChange, a hook for changed configuration files; reloadSystemd, which reloads background services; setupTrackedHooks, which installs git hooks; and syncPrBranchProtection, which synchronizes branch-protection settings. After all of them the script marks the new generation against Nix's garbage collector.

This module already treats the stop-on-failure rule as load-bearing. Its other entry, agentVmStatus, runs two helpers that can refuse to act: piStatusInstall, when the status file it would replace was written by the operator rather than the configuration, and claudeStatusMerge, when a settings file is not valid JSON. Both are invoked with a fallback that turns a refusal into a printed warning, and the source comment says why: a refusal must not abort activation or skip any entry sorted after this one.

Nix string context: how a file reference travels into a check

Nix quietly tracks which built files a string mentions, and that tracking is the entire reason a check running in an isolated sandbox can open the prompt file that a shell alias names.

Nix keeps every file it builds in one tree, conventionally /nix/store. Each entry is named by a hash and a label and is never modified once written. A path into that tree is a store path. Two helpers appear in this change: writeText, which writes text into the store as a file, and runCommand, which creates a build step that runs a shell script.

A build step runs in a sandbox: a stripped-down filesystem view in which the only store paths visible are the ones Nix decided the step depends on. A store path that the step merely mentions as text is not automatically there. This is the crux.

Splicing a built file into a Nix string does two things: it substitutes the store path, the visible part, and it attaches a hidden record of which built things that path came from. Nix calls that record the string's context, and it travels with the string through concatenation and through storage in a configuration option. When such a string is written out as a file, the context becomes a real dependency, and the mentioned file is pulled into the sandbox of anything using the result.

That was tested, not assumed. A small standalone build was written twice — context intact, then explicitly discarded. With the context intact it printed the file's contents; with the context discarded it failed with No such file or directory on a path it had just located by text search.

Tracing the prompt file from the module into the check's sandbox

  1. 1. The module builds the prompt file

    The instruction text for Claude Code is written into the store under the label claude-system-prompt-append — an ordinary built file with a store path.

  2. 2. The alias names that file

    The module defines a shell alias for the claude command that passes the prompt file with a flag. Building that string splices in the prompt file's store path, so the string carries a context recording that dependency.

  3. 3. The check writes the alias out as a file

    The check reads the alias string out of the developer machine's evaluated configuration and writes it into the store. Because of the context, the prompt file becomes a recorded dependency of that new file rather than text inside it.

  4. 4. The sandbox receives both files

    The check's build step uses the alias file, so Nix brings it and everything it depends on into the sandbox. The prompt file arrives with it.

  5. 5. The check extracts the path and reads it

    A search pulls the first store path ending in -claude-system-prompt-append out of the alias file, and the check reads that file. It inspects the same file a developer's shell would hand to Claude Code, not a copy.

The harness table, the mandatoryRead template, and workFile

Four artifacts that used to be written by hand, in three different wordings, now come from one list of three rows and one function that writes the mandatory-read sentence.

The three programs this module configures are terminal coding agents: Claude Code, Codex, and Pi. Each reads a file at startup for standing instructions — ~/.claude/CLAUDE.md, ~/.codex/AGENTS.md, and ~/.pi/agent/AGENTS.md respectively — and this module writes all three on every rebuild. They are called pointer files because they hold no instructions of their own: they point at files in the shared memory repositories, one adapter file per agent per repository.

Two memory repositories are checked out on a developer machine, listed in the module as memoryCheckouts: allod/memory and agent-memory. Each keeps an adapter file per agent under adapters/ and a top-level memory.md. Claude Code also receives text appended to its system prompt, because the shell alias for the claude command passes a prompt file on every launch.

What the four artifacts said before, and what they say now

Before this change, each of the three pointer blocks was written out separately, each with its own hand-written sentence of the form "Read shared instructions from" followed by a path. Only the appended prompt for Claude Code carried the strong wording — the sentence beginning "MANDATORY: Before responding to any user message" — and a fourth, unrelated piece of code assembled it, with its own list of paths and two closing sentences no other artifact had.

Following one row through to the bytes it produces

Take the Codex row from the table the source names harnesses. It gives three values: the display name Codex, the pointer file .codex/AGENTS.md relative to the home directory, and the adapter file adapters/codex/AGENTS.md relative to a memory checkout. A helper named workFile turns a checkout name and a file name into a full path by prefixing /home/, the account name, and /work/. Applied to both checkouts it yields two full paths.

Those two paths are handed to mandatoryRead, the single function that now writes the framing. It emits the mandatory-read sentence, then an empty line, then one numbered line per file with the path wrapped in backticks — and nothing else. Everything the old code had after the list is gone.

Why the paths became absolute, and what that costs

The appended prompt used to list allod/memory/memory.md and agent-memory/memory.md, followed by "Paths are relative to the primary working directory." Both the shell alias and the yolo wrapper change into ~/work before launching, so those relative paths did resolve on the launch routes this module provides. No broken launch is recorded in the change or its discussion, and the module's comment states the goal generally: every rendered artifact should resolve whatever directory the agent was launched from. The failure closed is therefore latent — an agent started by some other route, or one whose working directory moves mid-session — not observed. Why now is not recorded, so treat the motive as unverified.

The cost is real. A full path contains the account name, so the prompt file's content and its store path now differ between accounts, and the text cannot be copied to a machine whose account is named differently. The old form bought portability and paid with a dependency on the launcher's working directory; the new form makes the opposite trade. Since this module already writes the account name into the pointer paths and the symlink path, the new form makes the four artifacts consistent rather than adding a coupling.

Who states the topic-file reading rule

A topic file is one of the subject-specific documents a memory repository keeps beside its memory.md — one on git workflow, one on testing policy, and so on. The top of memory.md lists them under a heading, and something has to tell an agent to read the relevant ones. Until this change, the appended prompt said so, explaining that each file contains a topic file index whose relevant entries should be read.

That sentence is deleted here, and its one remaining author is the ## Topic Files section of memory.md in allod/memory, which since commit b633926 reads "Read the topic files relevant to the current task." The rule still reaches every agent through the adapter files: each one in allod/memory says to read memory.md first, and the pointer files now command the agent to read those adapter files. The commit before b633926 lacks the sentence — the condition under which the rule disappears entirely: a machine whose working copy was last pulled before it sees the rule from neither source once this merges. Nothing here inspects those working copies' revisions.

Evidence boundary

The allod/memory facts above were read from a checkout on the machine that produced this report: b633926 is the tip of its master branch and does add the sentence. The second checkout, agent-memory, is not present on this machine, so nothing here establishes what its adapter files or memory.md contain, or whether they exist at all on a developer machine.

The same framing arrives twice in one Claude Code session

Under the shell alias, a Claude Code session picks up ~/.claude/CLAUDE.md, which now carries the mandatory-read framing over two adapter files, and the appended prompt, which carries the same framing over two memory.md files. Four files are commanded before the first response, and the adapter files point back at the same memory.md files the prompt already named. Codex and Pi see the framing once, having no appended prompt. Whether the doubling was considered is not stated anywhere in the change; the source does say that every artifact telling an agent to read memory renders this one template over its own file list, making the doubling a consequence of the design.

Caution

The framing says not to start working until every file is read. If one of the four named files is missing on a machine, the instruction cannot be satisfied, and nothing here checks that the adapter files or the memory.md files exist. The paths are written into the artifacts unconditionally from the list of checkout names.

A fourth memory checkout is added to the list and a fourth row is added to the table. What does the new agent's pointer file contain?

  • A. A header line, the mandatory-read sentence, a blank line, then four numbered full paths, each indented four spaces

    Indentation is removed twice over: Nix strips the shared leading whitespace when it reads the source, and lines after the first in a spliced value were never indented. The quoted heredoc copies what it is given through unchanged.

  • B. The same header, then the mandatory-read sentence repeated once above each of four numbered full paths

    The template takes the whole list of files and emits the sentence once, followed by the numbered list. It is called once per artifact, not once per file, which is why the sentence count across the activation text equals the number of table rows.

  • C. Its header line, the mandatory-read sentence, a blank line, then four numbered full paths at the left margin

    The header comes from the block, the sentence and blank line from the template, and the list gets one numbered entry per checkout. Adding a checkout lengthens the list; adding a row adds a whole file of this shape.

  • D. One header line, the mandatory-read sentence, a blank line, then four numbered paths relative to the working directory

    Relative paths were the old form, used by the appended prompt alone, and this change removed them. The helper that builds each entry prepends the home directory and the work directory, so every path is complete from the filesystem root.

Why is stating the topic-file reading rule in both repositories worse than stating it only in allod/memory?

  • A. This repository cannot see the index the rule refers to, so its copy would keep asserting a shape that allod/memory is free to change

    The rule describes how to use a list that lives in the other repository. A second author with no view of that list goes stale silently, and nothing would detect the disagreement. Keeping the rule beside the list makes the two change together.

  • B. The pointer files are regenerated on every activation, so they cannot carry a rule whose wording is owned elsewhere

    Regeneration is not the obstacle; these files are rewritten from source text on every rebuild and can carry any sentence. The problem is that the sentence would be authored here while the thing it describes is authored there.

  • C. The build check refuses any generated artifact containing the phrase, so a second copy would fail the gate

    The check enforces the decision but is not the reason for it — this same change added it to hold the decision in place. A check that forbids a phrase is downstream of the argument for forbidding it.

  • D. Claude Code discards an instruction that appears in both the user memory file and the appended system prompt

    No such behavior is documented or relied on anywhere in this change. The mandatory-read framing itself now reaches a Claude Code session from both of those places at once, which the change treats as acceptable.

The memory symlink and the -T flag

Adding one letter to the command turns a case that used to succeed with the wrong result into a case that stops the rebuild, and the cost of that stop is bounded by what the rest of the activation had left to do.

A symbolic link is a filesystem entry whose content is a path: opening it opens whatever that path names. The first two lines of this activation entry create a directory under Claude Code's own bookkeeping area and put a link named memory inside it, pointing at the last memory checkout in the list.

The ln command carries flags. -s makes a symbolic link rather than a hard one. -f replaces an existing entry at the destination instead of refusing. -n means that if the destination is itself a symbolic link to a directory, replace the link rather than following it. The new flag, -T, means treat the destination as a plain name, never as a directory to create something inside.

That last distinction is where the old behavior went wrong. Without -T, when the destination is a real directory, ln reads the request as "put the link in there" and creates an entry inside it named after the target's last path component. It reports success: the path that was supposed to be a link is still a directory, with a link nobody asked for inside it.

When the destination is an ordinary symbolic link with the right target — the normal case on a machine that has rebuilt before — the flag changes nothing. That was checked too: repeating the command with -T over an existing correct link exits successfully and leaves the link as it was.

Two consequences pull in opposite directions. The abort is loud and immediate, which is the point: a directory at that path means an assumption about the home layout is already broken, and the old code hid that behind a successful exit. Against that, a fatal line at the top of the entry withholds work unrelated to symbolic links — which this module elsewhere prevents, guarding two helper invocations so their refusals cannot skip later entries. Why this line differs is not explained; the observable difference is that those helpers refuse in order to leave an operator's file byte-unchanged, with the rest of the home still correct, whereas here the link the configuration assumes does not exist.

Evidence boundary

Whether any machine has a real directory at that path was not measured. The discussion states the live path is a correct symbolic link, so no machine reaches the new failure on this rebuild; that claim is not independently confirmed here. The directory holding the link is one Claude Code writes its own session records into — on the machine that produced this report it holds transcripts and per-session subdirectories, all named with session identifiers rather than the word memory. That makes an accidental collision unlikely rather than impossible — an interpretation of observed naming, not a documented guarantee.

One collision source is self-inflicted. A machine that ever ran the old command against a real directory still has that directory, with the stray nested link inside, and the new command fails on every rebuild until somebody removes it by hand. That is the intended trade — a silent wrong state made visible — but it turns a one-time invisible defect into a repeating visible one.

The link path on some machine is already a real directory, so the first line of the entry now fails. What state are the three pointer files in after that rebuild?

  • A. All three are rewritten, because each block writes to a temporary name and renames it into place

    Writing to a temporary name and renaming protects a reader from seeing a partially written file while a block runs. It offers nothing when the block never starts, and none of the three starts once the script has stopped above them.

  • B. All three are truncated to empty, because their temporary files were created before the failure

    Nothing creates those temporary files ahead of time. Each is created by the redirection at the start of its own block, and every block is below the line that failed, so no temporary file exists.

  • C. Only Claude Code's file is rewritten, because its block runs before the link line

    The entry begins with the directory creation and the link, and the three blocks follow in table order. Claude Code's block is first among the three but still below the failing line.

  • D. None is rewritten; all three keep the content the last successful rebuild wrote

    The activation script stops at the first unguarded failure, so everything below that line is skipped. The machine stays on the previous generation's instruction text rather than acquiring a partially updated set.

What the pi-integration check pins, and what it leaves unpinned

The check inspects the exact text that ships rather than a copy of it, which makes its passes meaningful and its silences precise: everything it does not search for is unprotected.

A check in this repository is a build step that produces an empty output file if all its assertions hold and fails the build otherwise. The gate script, ./check.sh, builds every machine and every check in a separate process and reports all failures rather than stopping at the first. The file changed here, checks/pi-integration.nix, already read the developer machine's real activation text; this change extends it.

Two inputs make that possible. The first is the activation text, read out of the evaluated configuration as home.activation.llmMemoryLinks.data and written into the store so a text search can run over it. The second is the shell alias for the claude command, written out the same way — and, through the string context described earlier, dragging the appended prompt file into the sandbox with it. The check extracts the prompt's store path from the alias text and reads that file.

Evidence

This design follows a rule in allod/memory's testing policy: a check that rebuilds the generated artifact alongside the real one witnesses its own rebuild, not the code under test, so it should consume the same generator and swap only its inputs. Reading the prompt through the alias is the strongest form of that — the check cannot be looking at a different file than the shell hands to Claude Code, because it found the path in the shell's own alias.

The assertions this change adds

Six search the activation text: the Claude Code and Codex header lines, and both memory checkouts' adapter paths for each of those two agents; the Pi equivalents were already present. One counts lines containing the mandatory-read sentence and requires exactly three. One requires the literal ln -sfnT. One fails if the phrase "topic file" appears anywhere in the activation text, matched without regard to letter case. Five work on the prompt file: that the alias names a prompt at all, that the framing is present, that both memory.md paths appear in full and wrapped in backticks, and that "topic file" appears nowhere in it.

The count of three is a literal, not derived from the table's length. Adding a fourth agent row therefore fails the check with a message saying it expected the framing once per harness, three times, and got four. That names the rule and the observed number, so an author can work out that the literal needs updating; read cold, it describes a rendering fault rather than a check fallen behind the table. The check also gains no assertion about the new row's header or paths until someone writes those by hand.

One structural property makes the coverage less lopsided than the list suggests. The atomic rename is pinned for the Pi row only, but all three rows render through the same function, so any change that dropped it would drop it everywhere and the Pi assertion would catch it. Pinning one instance of a shared template covers the template.

Which regressions fire, and which pass unnoticed

What the two demonstrated sabotage runs establish

The discussion reports two deliberate breakages, each applied then undone: removing the strict flag, and re-adding a topic-file sentence to the prompt. Each time the check failed with the matching message, and after undoing it the extracted artifacts matched this branch's intended output exactly. That establishes that these two assertions are wired up and can go red — a check that never fails proves nothing. It does not establish that the others can fail, and the repository's testing policy says as much: one sabotage fixture per validator, not one per failure mode it rejects.

Which machines rebuild differently

This module is composed only by the builder for developer machines. The example fleet has four machine configurations, exactly one of them a developer machine. The change to the appended prompt's text changes that file's content, its store path, the alias string that names it, and therefore the user's home configuration and the developer machine's whole build recipe. Nothing propagates to the other three, because nothing else composes this module.

  • 4 machinescounts machine configurations in this repository's example fleet, excluding the installer image and all checks
  • 1 build recipe changedcounts machines whose top-level build recipe differs between the base and head commits, excluding differences in what a rebuild then writes
  • 3 files rewrittencounts pointer files rewritten on every activation, excluding the appended prompt, which is a built file rather than a written one
  • 134 fewer bytescounts the shrinkage of the appended prompt file only, excluding the pointer files, which grew

That one-of-four figure was measured, not assumed. Nix calls a machine's top-level build recipe a derivation, exposes it here as system.build.toplevel, and identifies it by a store path ending in .drv; two configurations with the same identifier are the same build. The base commit's tree was exported to a scratch directory and evaluated offline alongside the head commit, and the identifiers were compared for all four machines: three matched exactly, the developer machine's differed. The extended check was built at the head commit and succeeded. The appended prompt file was built from both commits and read byte for byte, giving the size figures above.

Rolling back

Reverting the single commit and rebuilding restores the previous text with nothing left over. The three pointer files are rewritten from scratch on every activation, so the old sentences return on the next rebuild; the appended prompt is a built file the alias names by path, so reverting points the alias back at the old one. The symbolic link returns to being created without the strict flag. A revert does not undo a directory an operator removed by hand in response to the new failure — but removing it was the correct repair either way, since the configuration intends a link at that path.

Suppose the alias string reached the check with its context discarded but its text unchanged. Where would the check first fail?

  • A. At the search for the prompt's store path, because the path would no longer appear in the alias text

    Discarding context removes only the hidden dependency record. The visible characters of the store path stay where they were, so the search succeeds and the extracted value is non-empty.

  • B. At the first read of the extracted path, because that file would not exist inside the sandbox

    The dependency record is what brings the prompt file into the build's isolated filesystem. Without it the path points at nothing the sandbox can see, and the first attempt to open it reports that no such file exists.

  • C. At evaluation time, because Nix refuses to write a store path into a file without its context

    Nix allows exactly this, which is why the operation that strips context is named for being unsafe. Evaluation completes normally and the problem surfaces only when something tries to use the path.

  • D. At the framing assertion, because a file outside the sandbox reads as empty rather than as missing

    An unreadable path is not an empty file. The read fails outright with a file-not-found error rather than returning nothing, so the failure arrives before any assertion about wording is reached.

Someone edits the module so the symlink points at the first memory checkout instead of the last, keeping every flag. What happens when the gate runs?

  • A. It fails, reporting that the memory symlink lost its strict flag

    That assertion searches for the flag text alone and the flags were not touched, so it still matches. An assertion pinning a command's options says nothing about its arguments.

  • B. It fails, reporting that a memory checkout is missing from the activation text

    Those assertions require specific adapter paths to be present, and all still are — the pointer blocks were not touched. None requires any path to be absent, so a changed target leaves every one satisfied.

  • C. It passes, because no assertion mentions the symlink's target path

    The only assertion about that line searches for the flags. The target is unpinned, so this regression ships green and would be found only by someone noticing the link resolves to the wrong repository.

  • D. It fails, because the count of mandatory-read sentences no longer matches the table

    The count is taken over the framing sentence in the pointer blocks, and editing the symlink line adds and removes none of them. That assertion responds to the number of table rows.

Why do the other three machines in the example fleet come out with unchanged build recipes, even though this module was rewritten?

  • A. Only the developer machine builder composes this module, so no other machine's configuration references anything it produces

    The rewritten source only reaches a machine that includes the module. A machine that never includes it has an identical configuration before and after, which is what the base-versus-head comparison showed for three of the four.

  • B. Activation text is written at rebuild time, so it never forms part of any machine's build recipe

    Activation text is part of the configuration and is baked into the build recipe like everything else. That is why the developer machine's recipe changed and why the check can read the exact text without running anything.

  • C. The instruction text is the only thing that changed, and text changes do not alter a build recipe

    Changing text changes the content of the built file, which changes its store path, which changes every recipe that names it. The appended prompt demonstrates that chain on the developer machine.

  • D. The check builds only the developer machine, so other machines were never evaluated for comparison

    The gate evaluates every machine, and the comparison reported here evaluated all four at both commits. Isolation comes from which machines compose the module, not from what the gate looks at.
