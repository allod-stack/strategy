# How we should develop changes that touch real machines

Merging code to master does not change any machine you run. Your VMs are built from a snapshot file that names an exact version of each repository, and nothing you merge reaches a machine until you update that snapshot and rebuild. That means the thing worth guarding was never the merge — it was the rebuild. So instead of holding work back in long-lived branches, we keep merging as we do now, but before each merge we run one command that answers a single question: does this change any machine I actually run? If the answer is no, it is safe to merge, because the code just sits there dormant. If the answer is yes, that is the moment to stop and look at which machine and why.

Two more things follow from that. Turning a dormant feature on is a separate, deliberate step, and it is the step that gets the scrutiny. And there should be one throwaway machine that takes every risky change before the machine you work from does, so a change that breaks a machine never breaks the one you need in order to fix it.

The rest of this document is the reasoning, the exact commands, the costs, and the alternatives that were considered and rejected. Read on only as far as you care to.

## The recommendation

*(Written before the plain-English rule existed; kept as the detailed form.)*

Keep developing against master. The dangerous act in your stack was never the merge — it is the deploy lock advance plus rebuild. `rebuild-vm-from-host` builds `${DEPLOY_FLAKE}#<name>` exactly as the checkout's committed lock stands; merging to any repo's master deploys nothing until the private deploy flake's lock is advanced. Your pain is real, but "don't merge mid-project" treats master as the deployment boundary when your own architecture already put that boundary somewhere better. So the proposal is three rules, not a new branching model:

1. **Land inert.** An arc step merges to master on the current cadence only when it provably changes no real machine — proven by the drv-diff you already used this week (`nix eval .#nixosConfigurations.<m>...toplevel.drvPath --override-input ...`), run over every machine in the composition root. A step that cannot land inert does not land early; it waits for the arc's activation step. This is trunk-based development with feature flags, translated: in this stack a "flag" is an inventory fact, "dark launch" is merged framework code no machine's data selects yet, and "flipping the flag" is a data change whose fleet diff names exactly the machines it converts.
2. **Gate activation.** Two events get a mandatory fleet diff with a stated expectation: merging an arc's activation PR (expected: exactly the intended machines change), and advancing the private deploy lock (expected: exactly the sum of what landed since the last advance). The expectation goes in the PR's existing `## Validation` section — no new artifact. The gate is mechanical: it prints which machines change; you judge whether that list is the intended one.
3. **Canary first.** One new standing machine *identity* — a name in private inventory with keys provisioned once — whose VM is disposable and rebuilt at will. Any change that must be proven by rebuilding or replacing a machine is proven on the canary before the machine you develop from takes it. Your dev machine is never first for anything, which is the generalization of the rule memory#35 just recorded for runtime migrations.

Your two hypotheses, evaluated honestly: the second dev machine is half right — the expensive part of a machine here is its identity (keys are human host ceremony), not the VM (machines rebuild from a clone), so a standing second *identity* with a disposable VM buys nearly everything a permanent second dev seat would, without the standing RAM cost or the split working state. And "don't merge mid-project" is the right instinct at the wrong boundary — it survives here as the narrow rule "a step that cannot land inert waits," which preserves its guarantee while keeping forward momentum and your per-PR review rhythm intact.

## Day one, concretely

**The gate, before any tooling exists.** From the private deploy checkout (authoritative), or `allod/deploy` for the public approximation agents can run:

```bash
# baseline = the committed lock (what rebuilds deploy); candidate = same + unmerged revs
for m in $(nix eval .#nixosConfigurations --apply builtins.attrNames --json | jq -r '.[]'); do
  base=$(nix eval ".#nixosConfigurations.$m.config.system.build.toplevel.drvPath" --raw)
  cand=$(nix eval ".#nixosConfigurations.$m.config.system.build.toplevel.drvPath" --raw \
    --override-input archetypes/vm \
    "git+https://forge.anarch.diy/allod/vm.git?ref=refs/heads/agent/vm-microvm-guest-split&rev=<full-rev>")
  [ "$base" = "$cand" ] && echo "$m unchanged" || echo "$m CHANGES"
done
```

Per-machine sequential eval is deliberate — `nix flake check` over the whole composition root peaks near 7 GiB and OOMs (`nix.md`). Transitive inputs override by path (`archetypes/vm`), direct ones by name. Quote the URL; `&` backgrounds otherwise. I validated this exact command today against `allod/deploy`: the transitive path syntax works, a warm eval is about 6 seconds per machine (call it 30 seconds for the four-machine public fleet, minutes cold), and `allod-dev` came out byte-identical (`i2bbywbv…-nixos-system-allod-dev` both sides) with vm#5's branch substituted at `783bf6a` — which is milestone 2's inertness proof, already in hand.

**The rules, as memory edits (three R0 PRs).** `git-workflow.md` gains a "Landing machine-affecting work" section: land inert or wait; activation PRs and deploy lock advances get a fleet diff with the expectation stated in `## Validation`; stacked cross-repo PRs pin the dependency branch in `flake.nix` (visible in review, as nexus#24 does today) and, because forge merges are fast-forward — verified: merged agent-branch heads like tools `agent/always-isolate` are literally master commits — the lock's rev survives landing unchanged and only the `flake.nix` URL needs a one-line flip commit after the dependency merges, before the consumer merges. `vm-provisioning.md` generalizes memory#35: the dev machine is never first; the canary takes every rebuild-proven change before it. The dev-plan template asks each milestone to state its expected fleet diff (usually "no real machine changes"), which is one line per milestone.

**The canary, once.** You (host-side, human-only): add the name to private inventory, key its secrets, `provision-vm-from-host <name>`. To test unmerged work on it without touching the deployed lock: a throwaway worktree of the private deploy repo, `nix flake lock --override-input <input> "git+https://…?rev=<rev>"` (writes a clean lock entry, per `nix.md`), then `DEPLOY_FLAKE=<worktree> rebuild-vm-from-host <canary>`. The deployed checkout's lock never moves; the worktree is deleted after. `DEPLOY_FLAKE` being an env var means this needs zero code.

## The four scenarios

**1. The six-repo arc with the machine-converting data change.** This proposal catches it twice, mechanically. Milestone 1's landing gate demands proof of inertness — the runtime fact with `allod-dev = "microvm"` *was* drv-inert at that point, so it passes, which is correct: nothing was wrong yet. The catch fires at the consuming step: milestone 4's stated expectation is "no real machine changes" (activation is milestone 6's job), and its fleet diff prints `allod-dev CHANGES` — the exact event a human happened to notice this week becomes a diff line the process demands before merge. It fires again at the deploy lock advance even if every merge gate were skipped, because the advance's expectation would not include a dev machine converting runtimes. Where it can still fail: the gate names machines, it does not judge them — if the expectation is carelessly written as "allod-dev changes, fine," the process has done its job and the human has not; and the authoritative run needs the private fleet, so until the deploy-side run is habitual (or mechanized as a check in the private deploy repo), skipping it is possible. The public template run partially covers even that: `allod-dev` exists in the public example fleet, so the public-side gate an agent runs would have named it too.

**2. Testing something that takes down your workspace.** The canary is the machine that gets rebuilt, replaced, or bricked — built from the same archetype as the machine under test (one identity, any shape: its inventory entry is data, and its keys are keyed to its name, not its archetype). You keep working on your dev machine throughout. When the change is proven, your dev machine adopts it as a rebuild-switch of a known-good config: minutes, with work committed and pushed first, which the workflow already demands. If the dev machine must be destructively reprovisioned, the canary — just proven on the new config — is the temporary seat, which is the grain of truth in the second-dev-machine hypothesis, obtained per-event instead of as standing cost. Where this fails plainly: changes to the hypervisor host itself have no canary — one physical machine, and its net is NixOS generation rollback at the console, not this process. And the canary carries no real workload, so a defect that only manifests against your actual workspace state (say, a store migration that eats uncommitted work) shows up on your machine, not the canary; the mitigation is the commit-early culture, not the canary.

**3. Two unrelated projects at once.** Workspace concurrency is already solved — `allod change begin -d` worktrees, the concurrent-agent arc. What made concurrency unsafe at the repo level was that a half-landed arc left master incoherent; under land-inert, every landed step is provably a no-op for every machine, so two arcs interleave on master the way trunk-based development intends: small conflicts early instead of a stack-against-stack rebase at the end. Cross-repo pins: each arc's intermediate PRs pin their own agent branches; `flake-status <input>` already flags INCONSISTENT pins across repos, and the landing flip-commits reconcile at land time. What still serializes: the canary is one machine, so two arcs both needing substrate tests queue on it (a second throwaway identity is possible but costs key ceremony each time), and two arcs rewriting the same contract collide at plan time, which no branching model fixes — that stays the pm board's job.

**4. A dead end after three of six repos merged.** The three landed steps are inert by construction — dormant framework surface, zero machine effect, nothing deployed ever changed. Backing out is optional and unhurried rather than urgent: revert PRs at leisure (mechanical, one per repo, human-merged), or leave the surface dormant with a tombstone issue naming it. Compare today, where three landed steps of an abandoned arc may sit in the next routine `flake-update-cascade` lock advance whether coherent or not. The honest residue: published is forever, so the dead steps stay in public history either way (reverts, never erasure); dormant surface confuses later work if nobody tombstones it; and a step that was *not* inert — landed under the "activation PR" exception — would need a real revert with a fleet diff of its own, though by construction there is at most one such step and it lands last, so the window is one PR wide.

## What it costs

- Per arc milestone: one fleet-diff run (minutes of eval) and one stated expectation line in the PR's `## Validation`. Non-arc, single-repo changes pay nothing new.
- Landing a six-repo arc is still a serialized human chain: merge, flip-commit, merge — roughly N merges and up to N-1 one-line commits, perhaps an hour of attention end to end. Fast-forward merges keep the lock revs stable through it, but the chain is not one click and this proposal does not pretend otherwise.
- The canary identity is new durable state: one inventory entry, keyed secrets, host RAM while it runs, and the discipline of deleting deploy worktrees after canary tests. Its keys join the precious set.
- New failure modes: gate rot (a gate that is skipped when inconvenient silently stops guarding — the mitigation is that it is genuinely cheap, and the deploy-lock-advance run can later be made structural as a check the private deploy repo carries); expectation rubber-stamping (reading `CHANGES` lines as noise); a forgotten flip commit leaves a master lock referencing a deleted agent branch, which breaks cold fetches — real, already possible today, surfaced by `flake-status` and by the landing checklist.
- What gets worse: master carries dormant surface during arcs and after dead ones; PR bodies grow a line; and the inert rule reintroduces waiting for the specific step that cannot land inert — the owner's serialisation, shrunk to where it is load-bearing.

## What it does not solve

- The host itself. `nexus` changes that can strand the physical machine have no canary; generation rollback is the whole net. Structurally solving it means a second physical box or a nested-virt staging host — deliberately not proposed; the constitution's minimalism says one person does not run redundant control planes for this adversary model.
- Drv-blind behavior. The fleet diff sees the closure, not the world: provisioning script behavior, secrets contents, external volume state, and anything else outside the derivation change with zero diff. Acceptance tests against generated artifacts (principle 13) and canary rebuilds remain the only nets there.
- Review throughput. Arcs are review-bound; landing inert changes nothing about how fast ten passes converge.
- The public/private relay. `allod patch receive` friction is untouched; the authoritative gate run stays on the private side because only it sees the real fleet.

## Tools work

Day one needs none — the loop above is runnable now, and `nix.md` already documents its parts. Week one: `tools/flake/fleet-diff`, sibling of `flake-status` in house style — args: deploy checkout, repeatable `--override input=url`, per-machine sequential eval, `unchanged`/`CHANGES` per machine, non-zero exit when anything changes so it composes with expectations. Roughly the size of `flake-status` (490 lines) plus fixtures; one PR, R2, one review pass. Defer any `allod change land` helper for the merge-chain fixups until the chain has been walked manually once — extract on second use. `flake-update-cascade --pr` already covers post-landing pin propagation; nothing forge-side changes; agents still cannot merge anything anywhere.

## Alternatives seriously considered and discarded

- **Freeze the arc: keep all PRs open, merge everything at the end (your stated middle ground).** Walked through all four scenarios it works, and it needs no new mechanism — but it pays continuously: six PRs aging against a moving master (add-commit reconciliation only, no force-push), worktrees and review state held open for weeks, momentum visibly parked, and its scenario-4 win over land-inert is small because inert steps are already nearly free to abandon. Its guarantee survives here as the narrow wait rule for non-inert steps. Discarded as the default, kept as the fallback.
- **Per-arc integration branches (`arc/<name>` in each repo, PRs target them, one final merge each).** Buys prompt intra-arc merging and a stable ref to pin — but the lock pins revs, not refs, so consumers re-lock on every arc-branch advance anyway; it adds server-side branch state per repo per arc, re-targeting ceremony, and a second landing (PR to arc, arc to master). For one person this is release-train cosplay. The same holds for a standing integration flake repo: it is state that drifts stale and duplicates what the open PRs already say. Compute the integration point on demand (fleet-diff over PR heads); store nothing. The transient deploy worktree for canary builds is exactly that standing point, created per test and deleted — that is all a "standing" integration environment is worth here.
- **A permanent second dev machine.** What it actually unlocks — working while your substrate is replaced — happens a few times a year; what it costs is standing: keys, an 8 GiB slice of a host that also runs the canary and every agent VM, and a second seat whose only unique state is uncommitted work, in a stack built so machines have no unique state. Cheap disposable machines beat it precisely because your machines rebuild from a clone; the one-time-keyed, standing-identity canary is the version of this idea that survives principle 9.
- **Monorepo consolidation.** It would genuinely dissolve the cross-repo pin problem — one repo, one lock, atomic arcs. It dies on the constitution, not on taste: per-repo capability scoping (public-only agents write some repos and not others), the fork charter ("a fork changes exactly the three data input URLs"), fresh-history public exports, and per-repo blast radius are all load-bearing repo boundaries. Rebuilding the security model to fix a workflow inconvenience inverts the priority order.
- **Merge queues, release trains, batched integration windows.** They solve contention between many writers for one trunk. There is one writer. Their cost is pure ceremony here.

One structural note for later, not now: if arcs keep growing, the recurring cost center is the landing chain's flip commits, and the durable fix is repos pinning each other by rev-only lock entries with `ref=master` originals (already documented in `nix.md`) so ff-landing needs no flip at all — at the price of cold fetches failing until the dependency lands. Live with the flip commits first; adopt rev-only pins only if they annoy you twice.
